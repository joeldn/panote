# Design Decisions

Key decisions and their rationale, for panote. When a decision is superseded, the row is rewritten in place with the old choice noted inline — history stays visible without a separate changelog.

---

| Decision | Rationale |
|---|---|
| All-Cloudflare (Workers, Workers Static Assets, R2, Durable Objects, Queues, Containers) over AWS (supersedes: Pages for the SPAs — see the frontend hosting row below) | R2's zero-egress serving is what makes a free hosted panorama service viable — egress is the dominant cost for tile-heavy image traffic. CloudFront/S3 egress scales linearly with popularity against no revenue, which breaks the "free" premise the moment the service gets popular. |
| Auth0 for auth | Managed auth avoids building and maintaining login, session, and token issuance ourselves. RS256 JWTs verify statelessly wherever identity is needed — `admin-api` and `upload-api` require a valid token on every route (`authenticate`), `public-api` verifies one when present but never requires it (`authenticateOptional`) — no shared secret, no database round trip per request. |
| Node 24, pnpm, turbo, TypeScript, Vitest as the base toolchain | Matches the sibling wasmbed monorepo's toolchain, so conventions and tooling knowledge transfer directly. Turbo gives cached, parallel builds across many small workspaces, which is exactly this repo's shape. |
| `apps/` + `services/` + `packages/` split (deviates from the template-guide we otherwise follow, which has no `apps/`) | An SPA is still a different kind of workspace from an API Worker even though both now deploy as Workers (supersedes: "a Pages SPA"): an app is a Vite + React build whose output is a static `dist/` served by an assets-only Worker, its config is build-time `VITE_*` env files rather than Wrangler `vars`/bindings, and it tests under jsdom rather than workerd. So it gets its own top-level directory rather than living under `services/` with the API Workers. |
| Scope-per-directory naming (`@panote/*`, `@internal/*`, `@service/*`, `@app/*`) | The package name alone answers "can I import this" and "does this ship" without opening the file. `@panote/*` may be published; `@internal/*` is repo-only; `@service/*` and `@app/*` are deployable. Mismatched scope vs. directory is treated as a bug. |
| **REST everywhere over GraphQL (superseded: was going to be GraphQL for admin-api)** | There is no database and no object graph to compose over — R2 plus prefix-listing IS the query layer. The entire admin surface is roughly 7 operations, and frontend and backend ship together from one monorepo. GraphQL would not even have fixed the one real N+1 (gallery metadata): a resolver would still perform N individual R2 GETs, and DataLoader cannot batch object-storage reads the way it batches DB queries. Type safety is achieved more cheaply with shared zod schemas (`@internal/contracts`, request *and* response) plus a thin hand-written, response-validating fetch client in `@internal/web-kit` (supersedes: Hono RPC `hc<AppType>`, which doesn't fit — `admin-api` registers its routes imperatively rather than as one chained expression, so `AppType` carries no route types without a rewrite, and the apps would type-depend on a `@service/*` package). Reversible — the contracts live in one package, so a future GraphQL layer would wrap them rather than replace them. |
| Splitting the existing `crud-worker` into `services/public-api` (anonymous-first) and `services/admin-api` (100% authed) | Lets each Worker take a different auth, caching, and rate-limit posture instead of branching on auth state inside one Worker. `public-api` is anonymous-first, not auth-free: `POST /api/tours/:tourId/like` calls `authenticateOptional` to dedupe a logged-in caller's like by Auth0 sub, falling back to an `X-Client-Id` header when anonymous (`services/public-api/src/index.ts`) — but no `public-api` route *requires* a token, which is what keeps `admin-api`'s mandatory-auth path off it. `GET /api/tours/:tourId/stats` sets `cache-control: public, max-age=30`, which is necessary but not sufficient for edge caching — Cloudflare's Workers Cache doesn't store a dynamic response on that header alone without an explicit Cache API call or a caching rule for the route, neither of which exists yet, so today that header doesn't actually put anything in the edge cache. |
| `services/public-api` owns the `TourStats` Durable Object | View/like counters need a single consistent writer per tour; a Durable Object gives that without standing up a database. Keeping it on the anonymous API keeps the high-volume stats write path off `admin-api`'s auth-checked request path. |
| Large binary reads (tiles, manifests) and published tour JSON bypass the APIs and are fetched direct from an R2 custom-domain CDN | Routing large binaries through a Worker adds CPU-time billing and a latency hop for no benefit. R2's custom domain serves them directly with zero egress and Cloudflare's edge cache in front, keeping the API Workers focused on JSON. A WAF custom rule in front of the domain only lets `/tiles/`, `/pub/` and `/slugs/` through, so owner-scoped keys under `panos/`/`tours/` stay private. **Status: live in dev, outstanding in production** (supersedes: "not provisioned yet") — `cdn.panote.dev` is attached to `pano-content-dev` with the WAF rule verified; `cdn.panote.io` waits on production provisioning (`docs/deploy.md`). The SPAs take the base per environment from `VITE_CDN_BASE`. |
| One Cloudflare account; Wrangler named environments (dev → `panote.dev`, prod → `panote.io`); dev resources carry a `-dev` suffix | A single account avoids duplicating account-level config (DNS, WAF, Access policies) across accounts. Named environments give per-environment bindings inside one `wrangler.jsonc`. The `-dev` suffix stops dev and prod resources colliding in the same account's namespace — see the STANDARDS.md gotcha about named environments not inheriting top-level bindings. |
| Exact version pinning + a single pnpm catalog | One place a version can be written. Every workspace that depends on, say, `zod` references the catalog entry instead of repeating (and potentially drifting from) the version string. |
| Adopting the template-guide's tooling/structure conventions while dropping its AWS/K8s runtime chapters (gRPC, OTel NodeSDK, Pulumi, go-task, Buildkite) (Pulumi since re-adopted for the Cloudflare account itself, see the `infra/pulumi` row) | The tooling conventions (pnpm, turbo, exact pinning, Conventional Commits) are substrate-independent and worth keeping. The runtime chapters assume a Kubernetes/AWS deploy target; panote deploys only to Cloudflare Workers, so those chapters are simply wrong for this repo rather than adapted. |
| Test files get a separate `tsconfig.test.json` (`tsc -p`, `noEmit: true`) instead of being included in the build `tsconfig.json` | The build config sets `composite: true` and emits declarations via `tsc -b`, and `dist/` ships to consumers (or, for published packages, to npm) — a test file included there would compile straight into `dist/`. Excluding test files from the build config (as it already does) fixes that but silently drops them from `tsc` entirely, so `pnpm typecheck` never sees them. A second, `noEmit` config that layers on top of the package's own `tsconfig.json` (via TypeScript's array `extends`) gets both: test files are type-checked, and nothing new lands in `dist/`. |
| Tile pyramid bounds tightened to `tileSize ∈ {512, 1024}`, `faceSize <= 16384`, `maxLevel <= 5` (supersedes: `tileSize` any power of two in [128, 4096], `maxLevel <= 8`, no `faceSize` cap) | The provisional bounds from the original DoS fix (`878bc76`) didn't compose: `faceSize` and `maxLevel` bound different quantities, so `{tileSize: 128, maxLevel: 7, faceSize: 16384}` passed both checks while still driving the viewer's per-frame visibility loop to ~19.3 ms/frame. `faceSize <= 16384` is the perceptual limit — 182 texels/degree, screen-pixel-matched at the viewer's 15° minimum FOV on a 2160-device-pixel viewport, and it's also the storage/spend lever since bytes scale as `faceSize²`. `maxLevel <= 5` is the frame-budget limit — 6,144 visibility checks, ~1.39 ms/frame measured. `tileSize` is restricted to the two values that reach the `faceSize` cap exactly (`512·2⁵ = 1024·2⁴ = 16384`), so the three bounds compose with no dead combinations. |
| Generate Worker types with `wrangler types` instead of depending on `@cloudflare/workers-types` | Cloudflare deprecated the package in favour of binding-exact generated types: the CLI prints an "Action required" telling you to uninstall it, and the package's own README leads with the same note. The generated `worker-configuration.d.ts` knows the actual bindings — a Durable Object namespace is typed `DurableObjectNamespace<TourStats>` rather than the bare namespace, and only the vars that exist are declared — so a binding typo is a type error instead of a runtime `undefined`. The file is committed rather than gitignored so a cold clone type-checks with no codegen step and binding changes show up in review; each Worker carries a `types` script to regenerate it. |
| `admin-api` moves to `/api/admin/*`; `public-api` moves to `/api/tours/*` (`upload-api`'s `/api/upload-url` and `tiler-consumer`'s queue trigger are unaffected) | One hostname shared with the website and admin Workers (supersedes: "one Pages deployment"), and Cloudflare route patterns are prefix/wildcard based, so they cannot split `PUT /api/tours/:id` (admin) from `POST /api/tours/:id/view` (public) on path alone. Moving the admin surface under its own prefix makes each Worker's route pattern a clean, non-overlapping wildcard: `admin-api` → `<host>/api/admin/*`, `upload-api` → `<host>/api/upload-url`, `public-api` → `<host>/api/tours/*`. Declaring the actual `routes` blocks in `wrangler.jsonc` was Wave 4's job — done, the three HTTP Workers (`admin-api`, `public-api`, `upload-api`) now declare them (`tiler-consumer` is a queue consumer with no fetch handler, so it has none); see the row below for where they route to and `docs/deploy.md` for why none of them are actually live yet. |
| `TourStats` gets a brand-new, empty Durable Object namespace under `panote-public-api` rather than a `renamed_classes` migration from `pano-crud`'s namespace | A DO class is namespaced by the script that declares it, so view/like counters reset to zero. Accepted because only pano-viewer's *dev* Workers are deployed today, Wave 5 deploys panote's Workers as new scripts and then retires pano-viewer, and dev-only counters have no value worth a cross-script migration. |
| Only the owner segment of an R2 key is base64url (RFC 4648 §5, no `=` padding) of the UTF-8 Auth0 sub; `panoId`/`tourId` stay verbatim, restricted to `/^[A-Za-z0-9_-]+$/` (`PANO_PATTERN`) and validated at every API entry point (supersedes: `encodeURIComponent`) | R2 objects are reachable through two access paths that disagree about percent-encoding: the S3 API (`upload-api`'s presigned PUT, the tiler container's writes, via `packages/worker-kit/src/r2-s3.ts`) percent-decodes the key server-side, while the native R2 binding (`admin-api`, via `packages/worker-kit/src/r2-binding.ts`) treats a key as an opaque string with no decoding at all. A sub like `auth0\|abc123` percent-encoded to `auth0%7Cabc123`, so the two paths landed on two different physical objects for what was meant to be one key — base64url's alphabet (`A-Z a-z 0-9 - _`) contains no character either path treats specially, which is why the owner segment gets it. `panoId`/`tourId` deliberately do NOT: the tiler writes tiles and `manifest.json` under the owner-free `tiles/<panoId>/` prefix using the raw `pano` id (see the row below for why that prefix carries no owner segment at all), and the viewer builds tile URLs directly from the manifest's raw `pano` field — encoding that segment would change every tile URL the viewer constructs, not just the storage key. Restricting caller-supplied ids to `PANO_PATTERN` gets the same "never contains a `%`" safety property as encoding, without needing to decode it back out anywhere the id is used verbatim. `PANO_PATTERN` is exported from `packages/core/src/manifest.ts` and re-exported through `@internal/contracts`; four schema fields in `packages/contracts/src/schema.ts` enforce it via `.regex(PANO_PATTERN)` — `SceneConfigSchema.panoId`, `TourDocSchema.tourId`, `TourSceneSchema.panoId`, and `HotspotSchema.targetPanoId`; the key builders assert it again as a last line of defence (`assertValidId` in `packages/contracts/src/keys.ts`); `admin-api`'s `DELETE /api/admin/panos/:panoId`, `GET /api/admin/panos/:panoId`, and `GET /api/admin/tours/:tourId` handlers (in `services/admin-api/src/index.ts`) each check it explicitly and return 400 on a mismatch rather than letting `assertValidId`'s throw surface as a 500. Two contract tests pin the invariant this whole row exists for: `packages/worker-kit/src/r2-key-parity.contract.test.ts` (the S3 API path and the native R2 binding land on the identical key for the same input) and `services/tiler-consumer/src/key-contract.test.ts` (the tiler's upload keys equal the keys the viewer's `manifestUrl()`/`tilePath()` request, i.e. `panoId` surviving verbatim end-to-end). A read-only account probe on 2026-09-23 (`wrangler r2 bucket info pano-content-dev`) reported 0 objects; pano-viewer's live Workers share this bucket, but their upload route authenticates against the same placeholder Auth0 issuer as panote (no tenant exists for either), so it has always returned 401 and cannot have written any originals — so as of that probe, no data existed under the prior `encodeURIComponent` scheme and no migration was needed. That's a point-in-time fact, not a permanent guarantee (anyone with account access could put an object manually afterward), which is why `docs/deploy.md`'s first dev deploy checklist re-checks the object count immediately before the `tiler-consumer` cut-over rather than relying on this row. |
| Routes for `admin-api`/`public-api`/`upload-api` live on the site's own host (`panote.dev`/`panote.io`, same-origin with the frontend), and `workers_dev: false` and `preview_urls: false` in both envs (supersedes: `workers_dev: true` in dev for a smoke-test URL) | Confirmed and declared in Wave 4 — the three HTTP Workers now have `routes` blocks (`panote.dev/api/admin/*`, `panote.dev/api/tours/*`, `panote.dev/api/upload-url`, mirrored on `panote.io`); `tiler-consumer`, a queue consumer with no fetch handler, deliberately has none. Same-origin means no CORS middleware is needed in Worker request handling (R2 bucket CORS, covered in `docs/deploy.md`, is a separate, R2-level concern). `wrangler deploy` attaches a declared route as part of the deploy itself and fails if the route's zone isn't on the Cloudflare account, so `panote.dev` being an Active zone is a *prerequisite for the first dev deploy*, not something `workers_dev` works around — it's unverified whether a zone merely Pending (added but not yet Active) is enough for the route attach to succeed, so the instruction is to wait for Active regardless. `dev` used to keep `workers_dev: true` as a second smoke-test URL, but since `panote.dev` went behind Cloudflare Access (2026-10-06) the public `*.workers.dev` and Preview URLs bypassed the gate, so both are off in `dev` (2026-10-08); smoke tests use `panote.dev/api/*`, which the Access bypass keeps open (`docs/deploy.md`, Cloudflare Access). `production`'s `workers_dev` and `preview_urls` are `false` since it's only ever reachable via its route. |
| The two SPAs (`apps/website`, `apps/admin`) are assets-only Workers (Workers Static Assets) on the same host as the APIs — `panote-website[-dev]` on `panote.dev/*`, `panote-admin[-dev]` on `panote.dev/app` + `panote.dev/app/*` (mirrored on `panote.io`) — with `not_found_handling: "single-page-application"` and per-environment config in committed Vite env files (`.env.dev`, `.env.production`, built with `vite build --mode <env>`) (supersedes: Pages SPAs) | One routing mechanism and one deploy path (`wrangler deploy --env`, the `deploy-apps` job in `.github/workflows/deploy.yml`) for all Workers, and the same-origin/no-CORS decision above still holds, which also lets the website and admin share one Auth0 session. Cloudflare picks the most specific route pattern when several match ("When more than one route pattern could match a request URL, the most specific route pattern wins", https://developers.cloudflare.com/workers/configuration/routing/routes/#matching-behavior), so the API Workers' `/api/admin/*`, `/api/tours/*` and `/api/upload-url` routes and admin's `/app` routes keep their traffic and only the rest falls through to the website. Admin uses two patterns, `/app` and `/app/*`, instead of the single `app*`, which would also swallow `/apple`, `/application` and so on. Pages was rejected as a second deploy system with its own project/branch model and custom-domain attachment beside the Worker routes; a runtime `/config.json` was rejected as an extra request on boot that would force a Worker script onto both apps. Build-time env means a config change needs a rebuild, and the `YOUR_` guard scans `apps/*/.env.production` as well as every `wrangler.jsonc`. |
| Deploy workflow (`.github/workflows/deploy.yml`) auto-deploys `dev` via a `workflow_run` trigger, gated on `CI` concluding `success` for a `push`-triggered run in this repo, the repo variable `DEV_AUTO_DEPLOY` being `true`, and that run's commit still being `main`'s current tip (supersedes: `workflow_dispatch`-only for both environments); `production` stays `workflow_dispatch`-only (`environment` input, default `dev`), additionally hard-guarded to `main`, hard-stopped unless the repo variable `PRODUCTION_PROVISIONED` is `true`, and fails closed if any service's config still has a `YOUR_` placeholder | Before the Wave 5 queue cut-over, every deploy, dev included, was a deliberate manual action in practice — the `dev` queue consumer slot was held by pano-viewer's old `pano-tiler-dev` Worker (a queue allows exactly one consumer), so an automatic dev deploy of `tiler-consumer` would have failed on every trigger until that cut-over happened (see the `deploy-tiler-consumer` job comment in `.github/workflows/deploy.yml`), which is why `DEV_AUTO_DEPLOY` stayed unset until both the first manual dev deploy and the cut-over had succeeded. Both are done as of 2026-09-26 (`docs/deploy.md`), and `DEV_AUTO_DEPLOY` is now `true`. `workflow_run` only fires from `main`'s own copy of the workflow file (GitHub always evaluates it off the default branch), and `resolve-environment`'s gate requires all of: `CI`'s run *concluded* `success` (not merely completed), that run was itself triggered by a `push` (so `CI`'s weekly `schedule` run and a manual `workflow_dispatch` re-run of `CI` never deploy), the run's head repository is this one (not a fork), and `DEV_AUTO_DEPLOY` is `true`. Even then, `resolve-environment` re-checks (`gh api repos/<owner>/<repo>/commits/main`) that the commit `CI` ran against is still `main`'s current tip — two pushes' `CI` runs can finish out of order, so without that check a `CI` run for an older commit finishing late would redeploy it over a newer commit already live; a stale run instead emits a `::notice::` naming both SHAs and skips the deploy jobs rather than failing. It always targets `dev` and can never resolve to `production`, and it checks out the exact commit `CI` verified (`github.event.workflow_run.head_sha`), not whatever `main` has moved to since. `production` needs a human in the loop regardless (the GitHub Environment's required reviewers gate it, backed by a workflow-level `::error::` guard — the `resolve-environment` job's "Guard deploys to main" step — that fails the run outright if `github.ref` isn't `refs/heads/main`; it guards `dev` dispatches too, since the `dev` token is on the same Cloudflare account and can't be scoped away from production). It's also hard-stopped unless the repo variable `PRODUCTION_PROVISIONED` is the literal string `true` (the `resolve-environment` job's "Fail unless production is provisioned" step) — nothing downstream can otherwise tell "provisioned" from "not provisioned" on its own, so without this gate `wrangler deploy` would simply fail mid-matrix against whichever resource happens to be missing for whichever service deploys first; the variable is set once, by hand, only after `docs/deploy.md`'s one-time production provisioning is actually done. And a `YOUR_` placeholder reaching production — the Auth0 issuer especially — would either 401 every authenticated request or, worse, tempt someone into "tidying" it into another fake-but-claimable tenant name, which would be a silent auth bypass; the workflow greps all four services' and both apps' `wrangler.jsonc` `env.production` blocks, plus each app's `.env.production`, for `YOUR_` in one case-insensitive check (the `resolve-environment` job's "Fail if any production config still has a YOUR_ placeholder" step), run once rather than duplicated per deploy job — `deploy-workers`, `deploy-tiler-consumer` and `deploy-apps` all `need` that job, so this one check failing blocks every deploy, including `tiler-consumer`'s. That's deliberate: `tiler-consumer`'s own `wrangler.jsonc` has no `OAUTH_ISSUER` var at all, so a per-service check would find nothing to flag on its config and let it deploy to an otherwise-unprovisioned production regardless of the other three services' placeholders. |
| `OAUTH_ISSUER` ships as a literal placeholder in `production` (`https://YOUR_PROD_TENANT.auth0.com/`) until its Auth0 tenant exists, and `authenticate()` rejects an unconfigured or placeholder-shaped issuer before any network call (supersedes: `dev` also shipped a placeholder, `https://YOUR_DEV_TENANT.auth0.com/`, until the `panote-dev.au.auth0.com` tenant was provisioned on 2026-09-25) | `dev` now points at the real `panote-dev.au.auth0.com` tenant (`OAUTH_AUDIENCE` `https://api.panote.dev`); no production Auth0 tenant exists yet (still a prerequisite for a production upload/admin flow). Without an explicit guard, an unconfigured issuer would still eventually 401 — `makeJwksLoader`/`verifyWithRotation` fail against it — but only after an outbound fetch to the placeholder host on every authenticated request (Auth0's wildcard DNS answers it, so it isn't even a fast local failure), and an empty issuer throws an opaque `TypeError` instead of a clean 401. `isIssuerConfigured` (`packages/worker-kit/src/auth.ts`) checks first, logs one `console.error`, and throws `UnauthorizedError` — every authenticated request is rejected the same way whether the issuer is missing, empty, non-https, or the shipped placeholder. The placeholder must only ever be replaced by the real tenant URL, never renamed to another fake-but-claimable tenant name — a name someone else could register would let their tokens verify successfully against it. |
| Tiles and the manifest live at the owner-free `tiles/<panoId>/`, with versioned tile dirs `tiles/<panoId>/t<TILER_OUTPUT_VERSION>-<original ETag>/` and the manifest at `tiles/<panoId>/manifest.json` (supersedes: tiles/manifest under the owner-scoped `panos/<owner>/<panoId>/` prefix) | `base64url(sub)` is reversible, so a public tile URL under `panos/<owner>/` would leak the Auth0 sub to anyone watching network traffic — an R2 custom domain serves the whole bucket, so there is no per-prefix access control to fall back on. `panoId` alone is enough of a namespace since it's a server-generated UUID, globally unique. panoId uniqueness is now a security invariant: originals must only ever be written under a server-generated panoId (`upload-api`'s `crypto.randomUUID()` with a key-pinned presign), and no route may accept a client-chosen panoId for an original. Versioned dirs (`packages/tiler/src/version.ts`'s `TILER_OUTPUT_VERSION` plus the original's ETag, derived in `services/tiler-consumer/src/container.ts`) let tile bytes stay immutable-cached forever while a re-tile — a new original, or a bumped `TILER_OUTPUT_VERSION` — writes to a fresh version dir and only swaps the short-cached `manifest.json` last, so a client never sees a manifest pointing at a partially-written version. Before that swap, the tiler HEADs the original (`packages/worker-kit/src/r2-s3.ts`'s `head()`) and skips the manifest write if it's gone or its ETag no longer matches what was tiled; it HEADs the original again right after the manifest PUT, and this time an ETag that comes back *different* (a newer original landed and was tiled after the pre-swap check, so this job's PUT may have overwritten the newer job's manifest) makes the job throw and retry instead of cleaning up, so the queue redelivers it and it rewrites the correct manifest — closing what would otherwise be a race a superseded job could lose. `admin-api`'s `DELETE /api/admin/panos/:panoId` (`services/admin-api/src/delete-pano.ts`) always returns 204 and is idempotent: without proof of ownership (no original, no tombstone under the caller's own prefix) it only cleans up the caller's own owner-scoped prefix and never touches `tiles/<panoId>/`; with proof (the original OR a tombstone key, `panos/<owner>/<panoId>/deleting`, left by an interrupted delete) it writes that tombstone first (unless one is already there), deletes the original, sweeps `tiles/<panoId>/` exactly once, then deletes the rest of the owner prefix, tombstone included, in one prefix delete. One sweep suffices: every tiler write precedes that job's own last HEAD of the original, so a write racing after `deletePano`'s delete of the original is caught by that job's own post-PUT HEAD finding it gone, not by a second admin-api sweep. The tiler's own orphan cleanup (`deleteKeys` in `services/tiler-consumer/src/container.ts`) deletes each key one at a time via the S3 API rather than in one batched request, accepted because it only ever runs during a delete race, not on any hot path; a single S3 multi-object delete call is a possible later optimisation. Superseded version dirs are deleted after a grace period, never on the swap itself (supersedes: left in place until the pano itself was deleted): once a job's post-PUT HEAD confirms its swap, it records every other dir under `tiles/<panoId>/` at `tile-gc/<panoId>/<version>.json` (overwritten on every swap so the record follows the latest one, `services/tiler-consumer/src/superseded.ts`; private, since the WAF doesn't serve `tile-gc/`), and `admin-api`'s 15-minute cron, after the backup and within the same R2 operation budget (`services/admin-api/src/tile-gc.ts`; supersedes: a daily run capped at 50 records), deletes those dirs once their record is over 24h old. A job that fails after it started uploading records its own partial dir the same way. The tiler never deletes another version itself, because a viewer that loaded the old manifest moments ago is still fetching its tiles (edge-cached ones would survive, uncached ones would 404 mid-session), and a dir it lists may be a newer job's still uploading — so a superseded job can't delete the winner's tiles. The sweep re-reads the manifest and never deletes the version it names, and keeps (re-checks on a later run) a dir the current original would tile into again (its ETag and the recording tiler version match the dir name), manifest or not, which covers an in-flight newer job and a retry of a failed first upload, and it keeps any dir with an object written after the record (an undo-replace or a tiler rollback rewrote it); an unreadable manifest also keeps everything. Deleting a pano deletes its `tile-gc/<panoId>/` records too, since they name the owner-bearing original key. No CDN purge: nothing references the old URLs any more. An original over `MAX_ORIGINAL_BYTES` is deleted once its `tile-failed` marker is written (the marker stays and reads as failed), unless the pano already has a manifest, where the original is the ownership proof for the live tiles. Originals that never tiled are not swept: they are the owner's photos, the library shows them as failed and the owner can delete them (a pending one past a day too), so deleting them automatically would lose data nobody asked to lose. `services/admin-api/scripts/account-storage.ts --tiles` reports them per account (and tile dirs no pano owns), and `retile.ts --pano` retries them. Bulk re-tiles go through `services/admin-api/scripts/retile.ts`, which puts the same message an R2 create event would on the upload queue, so originals are never rewritten. |
| Hotspot media is linked, never hosted: `img-src` and `media-src` allow `https:` in both apps' CSP, and `frame-src` allows only `www.youtube-nocookie.com` and `player.vimeo.com` (supersedes: CDN-only media, where `img-src`/`media-src` allowed just `'self'` and the CDN and any other host fell back to a plain link) | The editor's media picker offers image, audio, video, YouTube/Vimeo and link, and Panote stores only the url, so the media lives on whatever https host the author linked. A CDN-only policy made every such link a plain link, which made the feature pointless. Both apps get the same policy because the admin editor previews media inline exactly as visitors see it. The schema (`HotspotMediaSchema`) only stores `https://` urls without credentials, and the viewer refuses anything else, so `http:`, `data:` and `javascript:` urls never reach the page. Trade-offs: a linked host sees the visitor's IP and user agent when their media loads (and the page origin for audio, video and the players, which have no per-element `referrerpolicy` or refuse to play without one; images send no referrer), and `img-src https:` is a weaker barrier against image-beacon exfiltration in admin, where an injected `<img>` could reach any https host. Scripts, styles, `connect-src` and every other directive stay as strict as before. |
