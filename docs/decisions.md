# Design Decisions

Key decisions and their rationale, for panote. When a decision is superseded, the row is rewritten in place with the old choice noted inline — history stays visible without a separate changelog.

---

| Decision | Rationale |
|---|---|
| All-Cloudflare (Workers, R2, Durable Objects, Queues, Containers, Pages) over AWS | R2's zero-egress serving is what makes a free hosted panorama service viable — egress is the dominant cost for tile-heavy image traffic. CloudFront/S3 egress scales linearly with popularity against no revenue, which breaks the "free" premise the moment the service gets popular. |
| Auth0 for auth | Managed auth avoids building and maintaining login, session, and token issuance ourselves. RS256 JWTs verify statelessly in `admin-api` — no shared secret, no database round trip per request. |
| Node 24, pnpm, turbo, TypeScript, Vitest as the base toolchain | Matches the sibling wasmbed monorepo's toolchain, so conventions and tooling knowledge transfer directly. Turbo gives cached, parallel builds across many small workspaces, which is exactly this repo's shape. |
| `apps/` + `services/` + `packages/` split (deviates from the template-guide we otherwise follow, which has no `apps/`) | A Pages SPA is a different deploy target from a Worker — different build output, different runtime, different environment variables — so it gets its own top-level directory rather than living under `services/` with the Workers. |
| Scope-per-directory naming (`@panote/*`, `@internal/*`, `@service/*`, `@app/*`) | The package name alone answers "can I import this" and "does this ship" without opening the file. `@panote/*` may be published; `@internal/*` is repo-only; `@service/*` and `@app/*` are deployable. Mismatched scope vs. directory is treated as a bug. |
| **REST everywhere over GraphQL (superseded: was going to be GraphQL for admin-api)** | There is no database and no object graph to compose over — R2 plus prefix-listing IS the query layer. The entire admin surface is roughly 7 operations, and frontend and backend ship together from one monorepo. GraphQL would not even have fixed the one real N+1 (gallery metadata): a resolver would still perform N individual R2 GETs, and DataLoader cannot batch object-storage reads the way it batches DB queries. Type safety is achieved more cheaply with shared zod schemas (`@internal/contracts`) plus Hono RPC (`hc<AppType>`). Reversible — the contracts live in one package, so a future GraphQL layer would wrap them rather than replace them. |
| Splitting the existing `crud-worker` into `services/public-api` (anonymous) and `services/admin-api` (100% authed) | Lets each Worker take a different auth, caching, and rate-limit posture instead of branching on auth state inside one Worker. Cloudflare's Workers Cache only helps GET requests, so keeping `public-api` free of auth checks lets its GETs cache cleanly at the edge — a benefit `admin-api` doesn't need and shouldn't pay for. |
| `services/public-api` owns the `TourStats` Durable Object | View/like counters need a single consistent writer per tour; a Durable Object gives that without standing up a database. Keeping it on the anonymous API keeps the high-volume stats write path off `admin-api`'s auth-checked request path. |
| Large binary reads (tiles, manifests) bypass the APIs and are fetched direct from an R2 custom-domain CDN | Routing large binaries through a Worker adds CPU-time billing and a latency hop for no benefit. R2's custom domain serves them directly with zero egress and Cloudflare's edge cache in front, and it keeps both API Workers focused on JSON. |
| One Cloudflare account; Wrangler named environments (dev → `panote.dev`, prod → `panote.io`); dev resources carry a `-dev` suffix | A single account avoids duplicating account-level config (DNS, WAF, Access policies) across accounts. Named environments give per-environment bindings inside one `wrangler.jsonc`. The `-dev` suffix stops dev and prod resources colliding in the same account's namespace — see the STANDARDS.md gotcha about named environments not inheriting top-level bindings. |
| Exact version pinning + a single pnpm catalog | One place a version can be written. Every workspace that depends on, say, `zod` references the catalog entry instead of repeating (and potentially drifting from) the version string. |
| Adopting the template-guide's tooling/structure conventions while dropping its AWS/K8s runtime chapters (gRPC, OTel NodeSDK, Pulumi, go-task, Buildkite) | The tooling conventions (pnpm, turbo, exact pinning, Conventional Commits) are substrate-independent and worth keeping. The runtime chapters assume a Kubernetes/AWS deploy target; panote deploys to Workers and Pages, so those chapters are simply wrong for this repo rather than adapted. |
