# Design Decisions

Key decisions and their rationale, for panote. When a decision is superseded, the row is rewritten in place with the old choice noted inline — history stays visible without a separate changelog.

---

| Decision | Rationale |
|---|---|
| All-Cloudflare (Workers, R2, Durable Objects, Queues, Containers, Pages) over AWS | R2's zero-egress serving is what makes a free hosted panorama service viable — egress is the dominant cost for tile-heavy image traffic. CloudFront/S3 egress scales linearly with popularity against no revenue, which breaks the "free" premise the moment the service gets popular. |
| Auth0 for auth | Managed auth avoids building and maintaining login, session, and token issuance ourselves. RS256 JWTs verify statelessly wherever identity is needed — `admin-api` and `upload-api` require a valid token on every route (`authenticate`), `public-api` verifies one when present but never requires it (`authenticateOptional`) — no shared secret, no database round trip per request. |
| Node 24, pnpm, turbo, TypeScript, Vitest as the base toolchain | Matches the sibling wasmbed monorepo's toolchain, so conventions and tooling knowledge transfer directly. Turbo gives cached, parallel builds across many small workspaces, which is exactly this repo's shape. |
| `apps/` + `services/` + `packages/` split (deviates from the template-guide we otherwise follow, which has no `apps/`) | A Pages SPA is a different deploy target from a Worker — different build output, different runtime, different environment variables — so it gets its own top-level directory rather than living under `services/` with the Workers. |
| Scope-per-directory naming (`@panote/*`, `@internal/*`, `@service/*`, `@app/*`) | The package name alone answers "can I import this" and "does this ship" without opening the file. `@panote/*` may be published; `@internal/*` is repo-only; `@service/*` and `@app/*` are deployable. Mismatched scope vs. directory is treated as a bug. |
| **REST everywhere over GraphQL (superseded: was going to be GraphQL for admin-api)** | There is no database and no object graph to compose over — R2 plus prefix-listing IS the query layer. The entire admin surface is roughly 7 operations, and frontend and backend ship together from one monorepo. GraphQL would not even have fixed the one real N+1 (gallery metadata): a resolver would still perform N individual R2 GETs, and DataLoader cannot batch object-storage reads the way it batches DB queries. Type safety is achieved more cheaply with shared zod schemas (`@internal/contracts`) plus Hono RPC (`hc<AppType>`). Reversible — the contracts live in one package, so a future GraphQL layer would wrap them rather than replace them. |
| Splitting the existing `crud-worker` into `services/public-api` (anonymous-first) and `services/admin-api` (100% authed) | Lets each Worker take a different auth, caching, and rate-limit posture instead of branching on auth state inside one Worker. `public-api` is anonymous-first, not auth-free: `POST /api/tours/:tourId/like` calls `authenticateOptional` to dedupe a logged-in caller's like by Auth0 sub, falling back to an `X-Client-Id` header when anonymous (`services/public-api/src/index.ts`) — but no `public-api` route *requires* a token, which is what keeps `admin-api`'s mandatory-auth path off it. `GET /api/tours/:tourId/stats` sets `cache-control: public, max-age=30`, which is necessary but not sufficient for edge caching — Cloudflare's Workers Cache doesn't store a dynamic response on that header alone without an explicit Cache API call or a caching rule for the route, neither of which exists yet, so today that header doesn't actually put anything in the edge cache. |
| `services/public-api` owns the `TourStats` Durable Object | View/like counters need a single consistent writer per tour; a Durable Object gives that without standing up a database. Keeping it on the anonymous API keeps the high-volume stats write path off `admin-api`'s auth-checked request path. |
| Large binary reads (tiles, manifests) bypass the APIs and are meant to be fetched direct from an R2 custom-domain CDN | Routing large binaries through a Worker adds CPU-time billing and a latency hop for no benefit. R2's custom domain would serve them directly with zero egress and Cloudflare's edge cache in front, keeping both API Workers focused on JSON. **Status: not provisioned yet** — `cdn.panote.dev`/`cdn.panote.io` are manual per-environment dashboard steps (`docs/deploy.md`); neither exists, `pano-content-dev` currently has no custom domain, and its `r2.dev` access is disabled too, so there is no working read path for tiles/manifests today. |
| One Cloudflare account; Wrangler named environments (dev → `panote.dev`, prod → `panote.io`); dev resources carry a `-dev` suffix | A single account avoids duplicating account-level config (DNS, WAF, Access policies) across accounts. Named environments give per-environment bindings inside one `wrangler.jsonc`. The `-dev` suffix stops dev and prod resources colliding in the same account's namespace — see the STANDARDS.md gotcha about named environments not inheriting top-level bindings. |
| Exact version pinning + a single pnpm catalog | One place a version can be written. Every workspace that depends on, say, `zod` references the catalog entry instead of repeating (and potentially drifting from) the version string. |
| Adopting the template-guide's tooling/structure conventions while dropping its AWS/K8s runtime chapters (gRPC, OTel NodeSDK, Pulumi, go-task, Buildkite) | The tooling conventions (pnpm, turbo, exact pinning, Conventional Commits) are substrate-independent and worth keeping. The runtime chapters assume a Kubernetes/AWS deploy target; panote deploys to Workers and Pages, so those chapters are simply wrong for this repo rather than adapted. |
| Test files get a separate `tsconfig.test.json` (`tsc -p`, `noEmit: true`) instead of being included in the build `tsconfig.json` | The build config sets `composite: true` and emits declarations via `tsc -b`, and `dist/` ships to consumers (or, for published packages, to npm) — a test file included there would compile straight into `dist/`. Excluding test files from the build config (as it already does) fixes that but silently drops them from `tsc` entirely, so `pnpm typecheck` never sees them. A second, `noEmit` config that layers on top of the package's own `tsconfig.json` (via TypeScript's array `extends`) gets both: test files are type-checked, and nothing new lands in `dist/`. |
| Tile pyramid bounds tightened to `tileSize ∈ {512, 1024}`, `faceSize <= 16384`, `maxLevel <= 5` (supersedes: `tileSize` any power of two in [128, 4096], `maxLevel <= 8`, no `faceSize` cap) | The provisional bounds from the original DoS fix (`878bc76`) didn't compose: `faceSize` and `maxLevel` bound different quantities, so `{tileSize: 128, maxLevel: 7, faceSize: 16384}` passed both checks while still driving the viewer's per-frame visibility loop to ~19.3 ms/frame. `faceSize <= 16384` is the perceptual limit — 182 texels/degree, screen-pixel-matched at the viewer's 15° minimum FOV on a 2160-device-pixel viewport, and it's also the storage/spend lever since bytes scale as `faceSize²`. `maxLevel <= 5` is the frame-budget limit — 6,144 visibility checks, ~1.39 ms/frame measured. `tileSize` is restricted to the two values that reach the `faceSize` cap exactly (`512·2⁵ = 1024·2⁴ = 16384`), so the three bounds compose with no dead combinations. |
| Generate Worker types with `wrangler types` instead of depending on `@cloudflare/workers-types` | Cloudflare deprecated the package in favour of binding-exact generated types: the CLI prints an "Action required" telling you to uninstall it, and the package's own README leads with the same note. The generated `worker-configuration.d.ts` knows the actual bindings — a Durable Object namespace is typed `DurableObjectNamespace<TourStats>` rather than the bare namespace, and only the vars that exist are declared — so a binding typo is a type error instead of a runtime `undefined`. The file is committed rather than gitignored so a cold clone type-checks with no codegen step and binding changes show up in review; each Worker carries a `types` script to regenerate it. |
| `admin-api` moves to `/api/admin/*`; `public-api` moves to `/api/tours/*` (`upload-api`'s `/api/upload-url` and `tiler-consumer`'s queue trigger are unaffected) | One hostname, one Pages deployment, and Cloudflare route patterns are prefix/wildcard based, so they cannot split `PUT /api/tours/:id` (admin) from `POST /api/tours/:id/view` (public) on path alone. Moving the admin surface under its own prefix makes each Worker's route pattern a clean, non-overlapping wildcard: `admin-api` → `<host>/api/admin/*`, `upload-api` → `<host>/api/upload-url`, `public-api` → `<host>/api/tours/*`. Declaring the actual `routes` blocks in `wrangler.jsonc` was Wave 4's job — done, the three HTTP Workers (`admin-api`, `public-api`, `upload-api`) now declare them (`tiler-consumer` is a queue consumer with no fetch handler, so it has none); see the row below for where they route to and `docs/deploy.md` for why none of them are actually live yet. |
| `TourStats` gets a brand-new, empty Durable Object namespace under `panote-public-api` rather than a `renamed_classes` migration from `pano-crud`'s namespace | A DO class is namespaced by the script that declares it, so view/like counters reset to zero. Accepted because only pano-viewer's *dev* Workers are deployed today, Wave 5 deploys panote's Workers as new scripts and then retires pano-viewer, and dev-only counters have no value worth a cross-script migration. |
| Only the owner segment of an R2 key is base64url (RFC 4648 §5, no `=` padding) of the UTF-8 Auth0 sub; `panoId`/`tourId` stay verbatim, restricted to `/^[A-Za-z0-9_-]+$/` (`PANO_PATTERN`) and validated at every API entry point (supersedes: `encodeURIComponent`) | R2 objects are reachable through two access paths that disagree about percent-encoding: the S3 API (`upload-api`'s presigned PUT, the tiler container's writes, via `packages/worker-kit/src/r2-s3.ts`) percent-decodes the key server-side, while the native R2 binding (`admin-api`, via `packages/worker-kit/src/r2-binding.ts`) treats a key as an opaque string with no decoding at all. A sub like `auth0\|abc123` percent-encoded to `auth0%7Cabc123`, so the two paths landed on two different physical objects for what was meant to be one key — base64url's alphabet (`A-Z a-z 0-9 - _`) contains no character either path treats specially, which is why the owner segment gets it. `panoId`/`tourId` deliberately do NOT: the tiler writes tiles and `manifest.json` under the key prefix using the raw `pano` id, and the viewer builds tile URLs directly from the manifest's raw `pano` field — encoding that segment would change every tile URL the viewer constructs, not just the storage key. Restricting caller-supplied ids to `PANO_PATTERN` gets the same "never contains a `%`" safety property as encoding, without needing to decode it back out anywhere the id is used verbatim. `PANO_PATTERN` is exported from `packages/core/src/manifest.ts` and re-exported through `@internal/contracts`; four schema fields in `packages/contracts/src/schema.ts` enforce it via `.regex(PANO_PATTERN)` — `SceneConfigSchema.panoId`, `TourDocSchema.tourId`, `TourSceneSchema.panoId`, and `HotspotSchema.targetPanoId`; the key builders assert it again as a last line of defence (`assertValidId` in `packages/contracts/src/keys.ts`); `admin-api`'s `DELETE /api/admin/panos/:panoId` handler (in `services/admin-api/src/index.ts`) checks it explicitly and returns 400 on a mismatch rather than letting `assertValidId`'s throw surface as a 500. Two contract tests pin the invariant this whole row exists for: `packages/worker-kit/src/r2-key-parity.contract.test.ts` (the S3 API path and the native R2 binding land on the identical key for the same input) and `services/tiler-consumer/src/key-contract.test.ts` (the tiler's upload keys equal the keys the viewer's `manifestUrl()`/`tilePath()` request, i.e. `panoId` surviving verbatim end-to-end). A read-only account probe on 2026-09-23 (`wrangler r2 bucket info pano-content-dev`) reported 0 objects; pano-viewer's live Workers share this bucket, but their upload route authenticates against the same placeholder Auth0 issuer as panote (no tenant exists for either), so it has always returned 401 and cannot have written any originals — so as of that probe, no data existed under the prior `encodeURIComponent` scheme and no migration was needed. That's a point-in-time fact, not a permanent guarantee (anyone with account access could put an object manually afterward), which is why `docs/deploy.md`'s first dev deploy checklist re-checks the object count immediately before the `tiler-consumer` cut-over rather than relying on this row. |
| Routes for `admin-api`/`public-api`/`upload-api` live on the site's own host (`panote.dev`/`panote.io`, same-origin with the frontend), and `workers_dev` stays `true` in `dev` even with routes declared | Confirmed and declared in Wave 4 — the three HTTP Workers now have `routes` blocks (`panote.dev/api/admin/*`, `panote.dev/api/tours/*`, `panote.dev/api/upload-url`, mirrored on `panote.io`); `tiler-consumer`, a queue consumer with no fetch handler, deliberately has none. Same-origin means no CORS middleware is needed in Worker request handling (R2 bucket CORS, covered in `docs/deploy.md`, is a separate, R2-level concern). `wrangler deploy` attaches a declared route as part of the deploy itself and fails if the route's zone isn't on the Cloudflare account, so `panote.dev` being an Active zone is a *prerequisite for the first dev deploy*, not something `dev`'s `workers_dev: true` works around — it's unverified whether a zone merely Pending (added but not yet Active) is enough for the route attach to succeed, so the instruction is to wait for Active regardless. `workers_dev: true` gives a second, always-reachable `*.workers.dev` URL for smoke tests once the Worker is actually deployed; `production`'s `workers_dev` is `false` since it's only ever reachable via its route. |
| Deploy workflow (`.github/workflows/deploy.yml`) is `workflow_dispatch`-only for BOTH environments (`environment` input, default `dev`) until the Wave 5 queue cut-over; `production` is additionally hard-guarded to `main`, hard-stopped unless the repo variable `PRODUCTION_PROVISIONED` is `true`, and fails closed if any service's config still has a `YOUR_` placeholder | Every deploy today, dev included, is a deliberate manual action — the `dev` queue consumer slot is still held by pano-viewer's old `pano-tiler-dev` Worker (a queue allows exactly one consumer), so an automatic dev deploy of `tiler-consumer` would fail on every trigger until that cut-over happens (see the `deploy-tiler-consumer` job comment in `.github/workflows/deploy.yml`). Wave 5 turns dev auto-deploy on, and — per the same file's header comment — the intent is to gate it on CI success on `main` (`workflow_run`) rather than a raw `push`, so a broken build on `main` can't auto-deploy; no such trigger exists yet, so there's nothing to turn "back" on. `production` needs a human in the loop regardless (the GitHub Environment's required reviewers gate it, backed by a workflow-level `::error::` guard — the `resolve-environment` job's "Guard production to main" step — that fails the run outright if `github.ref` isn't `refs/heads/main`). It's also hard-stopped unless the repo variable `PRODUCTION_PROVISIONED` is the literal string `true` (the `resolve-environment` job's "Fail unless production is provisioned" step) — nothing downstream can otherwise tell "provisioned" from "not provisioned" on its own, so without this gate `wrangler deploy` would simply fail mid-matrix against whichever resource happens to be missing for whichever service deploys first; the variable is set once, by hand, only after `docs/deploy.md`'s one-time production provisioning is actually done. And a `YOUR_` placeholder reaching production — the Auth0 issuer especially — would either 401 every authenticated request or, worse, tempt someone into "tidying" it into another fake-but-claimable tenant name, which would be a silent auth bypass; the workflow greps all four services' `wrangler.jsonc` `env.production` blocks for `YOUR_` in one case-insensitive check (the `resolve-environment` job's "Fail if any production config still has a YOUR_ placeholder" step), run once rather than duplicated per deploy job — both `deploy-workers` and `deploy-tiler-consumer` `need` that job, so this one check failing blocks every deploy, including `tiler-consumer`'s. That's deliberate: `tiler-consumer`'s own `wrangler.jsonc` has no `OAUTH_ISSUER` var at all, so a per-service check would find nothing to flag on its config and let it deploy to an otherwise-unprovisioned production regardless of the other three services' placeholders. |
| `OAUTH_ISSUER` ships as a literal placeholder (`https://YOUR_DEV_TENANT.auth0.com/` / `https://YOUR_PROD_TENANT.auth0.com/`) until an Auth0 tenant exists, and `authenticate()` rejects it before any network call | No Auth0 tenant exists yet (a Wave 5 prerequisite for any upload/admin flow). Without an explicit guard, an unconfigured issuer would still eventually 401 — `makeJwksLoader`/`verifyWithRotation` fail against it — but only after an outbound fetch to the placeholder host on every authenticated request (Auth0's wildcard DNS answers it, so it isn't even a fast local failure), and an empty issuer throws an opaque `TypeError` instead of a clean 401. `isIssuerConfigured` (`packages/worker-kit/src/auth.ts`) checks first, logs one `console.error`, and throws `UnauthorizedError` — every authenticated request is rejected the same way whether the issuer is missing, empty, non-https, or the shipped placeholder. The placeholder must only ever be replaced by the real tenant URL, never renamed to another fake-but-claimable tenant name — a name someone else could register would let their tokens verify successfully against it. |
